### M0-R3-F01  Low  Operability  Pinned kubectl is appended to the user PATH but Docker Desktop's kubectl is on the machine PATH, so on this workstation the pinned copy can never win and the printed remedy is impossible
Location: `scripts/setup-windows.ps1:147-157`; `docs/toolchain.md:37`; `[Environment]::GetEnvironmentVariable('Path','Machine')` contains `C:\Program Files\Docker\Docker\resources\bin`; `where.exe kubectl` → that directory
Problem: Windows resolves the machine PATH before the user PATH. `Ensure-PinnedBinary` appends `%LOCALAPPDATA%\ivp\bin` to the *user* PATH (`:150`), so `kubectl` will resolve to Docker Desktop's 1.32.2 in every new terminal regardless of where the user-PATH entry sits, and `check-toolchain.ps1` will keep reporting `OUT OF RANGE` for a tool the installer just verified and installed — the exact loop R2-F01 described, now for one tool and one cause. The warning text (`:156`) says "move `$PinnedBin` ahead of it", which is not possible for a user-scope entry against a machine-scope entry. The shadowing warning itself only fires when the *current process* resolves the command, which happens here (Docker's kubectl is visible) but would not on a clean machine where the newly written user PATH is not yet in the process environment — harmless there because nothing shadows. Additionally the PATH block runs even when the download/verify failed (`:140-146` continues to `:148`), adding an empty directory to PATH.
Remediation direction: Detect the scope of the shadowing entry and print the actually-workable instruction ("remove `<dir>` from the Machine PATH (admin) or uninstall Docker Desktop's kubectl"), or have `check-toolchain.ps1` probe `$PinnedBin\kubectl.exe` and `talosctl.exe` directly for the two pinned tools and report both "on PATH" and "pinned" versions; skip the PATH block when the install failed.
Status: Open

### M0-R3-F04  Nit  Code quality  Minor robustness gaps in `setup-windows.ps1`
Location: `scripts/setup-windows.ps1:83-84,131-132,150,74-78`
Problem: (a) `Get-ExpectedDigest`'s `[Parameter(Mandatory)] [string]$Text` rejects an empty string, so a 200 response with an empty body produces "Cannot bind argument to parameter 'Text'" rather than "no digest"; it is caught by the surrounding `try` in both modes, so it fails closed, but the message misleads. (b) The `(?m)…\s+\*?name\s*$` regex lets `\s+` span a newline, so a file with the hash on one line and the name on the next would match; no real upstream file has that shape, but the sibling bash function does not accept it either, so the two disagree. (c) `Invoke-WebRequest -OutFile` for 60–120 MB files under Windows PowerShell 5.1 with the default `$ProgressPreference` is notoriously slow (progress rendering per buffer); `$ProgressPreference='SilentlyContinue'` in the function is the standard fix. (d) `[Environment]::SetEnvironmentVariable(…,'User')` rewrites the user PATH as `REG_SZ`, expanding any `%VAR%` entries. (e) Per R2-F05, a `0x8A15002B` "no applicable upgrade" exit is reported only as a number.
Remediation direction: `[AllowEmptyString()]` on `$Text`, replace `\s+` with `[ \t]+`, set `$ProgressPreference` locally, and map the common winget HRESULTs to one-line explanations.
Status: Open

## What was done well
- The Go fix is the right fix, not a patch: the digest comes from the same host that serves the tarball, in plain text, and Go and kubectl were folded into the common `verify()` path instead of keeping an inline `sha256sum -c` special case — one function to test, and I tested it against the real 70 MB artefact.
- `--check` now proves what the evidence claims: it downloads every checksum file and asserts a 64-hex digest for the exact asset name, and HEADs artefacts rejecting `text/html`. I reproduced the builder's negative transcript from a temp copy and it fails exactly as recorded; the round-2 bug could not recur silently.
- `expected_digest` returning 0 with empty output (`setup-wsl.sh:88`) and `grep … || true` (`:85`) are the correct idioms for lookups inside `$(...)` under `set -e`; the builder found this class of bug twice by running negative tests and fixed it at the root rather than by dropping `set -e`.
- `Ensure-PinnedBinary` compares the installed binary's own reported version to `PIN_*` (`setup-windows.ps1:121-124`) rather than "something is on PATH", which is what makes installer and checker agree by construction on Windows.
- The builder ran `setup-wsl.sh cluster` end-to-end into a throwaway `HOME` from Git bash to get real install-mode evidence on a machine that cannot run Linux — a creative and legitimate way to exercise the download/verify/install mechanics; my re-run with kubectl unhidden confirmed the one branch it skipped.
- The CI sops job now has the shape a gate should have: the helper's exit code is load-bearing, the tool version is printed for diagnosis, and the vacuous case is loud (`::warning`) rather than silent.
- The recipient-removal runbook uses the single atomic primitive that revokes a recipient and says why the follow-up `updatekeys` "adds nothing back" — the sentence that stops an operator from reasoning "I already ran updatekeys, so I'm done".
