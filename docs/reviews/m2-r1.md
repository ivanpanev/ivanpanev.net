## Verdict

Overall: 7 — FAIL
Code quality: 8 | Scalability: 8 | Reliability: 7 | Future-proofing: 8 | Security: 7 | Operability: 7

The two Terraform roots are coherent, formatted, valid, and aligned with ADR-0004/0005 on paper: no kube-API or CCM load balancer, APIs firewalled to the apply machine or an explicit CIDR, one `hostnames` map driving DNS + tunnel + Access, age-encrypted etcd snapshots into `ivp-etcd`, delete protection on by default. The milestone still fails because the operator-facing procedures that *are* in scope do not work as written: `terraform plan -destroy` cannot succeed while buckets in the same root have `lifecycle.prevent_destroy`, and the tunnel-token SOPS commands encrypt a `/tmp` path that does not match `.sops.yaml`. Those are the things that will bite at 3 a.m. or on first apply-plus-commit. Fix the teardown targeting (or split buckets into their own root), encrypt the Secret on the git path so creation rules apply, and turn the Access/rate-limit invariants into variable validations that actually fail the plan; that is what moves this to a 9.

## Findings

### M2-R1-F01  Medium  Operability  Full destroy cannot keep protected buckets
Location: `docs/runbooks/cluster-teardown.md:31-41`; `infra/terraform/hetzner/buckets.tf:15-19`
Problem: Buckets live in the same root as the cluster and have `lifecycle.prevent_destroy = true`. `terraform plan -destroy` includes those resources and fails with “Instance cannot be destroyed” (HashiCorp’s documented behaviour; the error tells you to disable `prevent_destroy` or use `-target`). The runbook instead says to confirm buckets are *not* in the destroy set and to stop if they appear — so a stranger cannot decommission or rebuild the cluster from the written procedure without either wiping backup buckets or inventing `-target=module.kubernetes`.
Remediation direction: Document a targeted destroy of `module.kubernetes` (and any other non-bucket resources), or move buckets into a separate state root. Do not instruct the operator to remove `prevent_destroy` as part of a cluster rebuild.
Status: Open

### M2-R1-F02  Medium  Security  Tunnel-token SOPS encrypt misses `.sops.yaml`
Location: `docs/runbooks/cluster-bootstrap.md:97-114`; `.sops.yaml:29-36`; contrast `docs/runbooks/secrets.md:25-39`
Problem: The mandated procedure writes a Secret under `/tmp/tunnel.secret.yaml` and runs `sops --encrypt` on that path. Creation rules match `^k8s/.*\.(enc|secret)\.ya?ml$` or `\.enc\.[a-z0-9]+$`, not `/tmp/tunnel.secret.yaml`. SOPS will error (no `--age` passed) or encrypt with the wrong recipients/regex. The operator is one workaround away from committing plaintext `TUNNEL_TOKEN`; hygiene would catch an unencrypted `tunnel.enc.yaml` only *after* it is named and placed under `k8s/`.
Remediation direction: Write the manifest at `k8s/infrastructure/cloudflared/tunnel.secret.yaml` (or `tunnel.enc.yaml`) and encrypt in place so `.sops.yaml` applies, as `secrets.md` already shows. Then `sops filestatus`.
Status: Open

### M2-R1-F03  Medium  Reliability  Notes-api rate-limit defaults may not apply
Location: `infra/terraform/cloudflare/rate_limit.tf:16-21`; `infra/terraform/cloudflare/variables.tf:78-87`; `docs/runbooks/cluster-bootstrap.md:86-88`
Problem: The ruleset uses `phase = "http_ratelimit"` with `period = 60` and `mitigation_timeout = 60`. Cloudflare Free (one rate-limiting rule) commonly accepts only `period`/`mitigation_timeout` of 10. The runbook never states the required zone plan. On Free, Cloudflare apply fails and the M2 rate-limit criterion is not delivered; on Pro it is fine.
Remediation direction: Record the intended Cloudflare plan next to the resource, and either default to Free-legal 10-second windows or fail fast in a comment/validation the operator will see before apply.
Status: Open

### M2-R1-F04  Low  Security  ADR-0005 “plan-time” checks do not fail the plan
Location: `infra/terraform/cloudflare/locals.tf:26-48`; Terraform 1.5+ `check` blocks warn and continue
Problem: The grafana/argocd/hubble and notes-api assertions are `check` blocks. A tfvars change that sets `grafana.public = true` or drops `notes-api.rate_limit` still applies; Terraform only warns. The hostnames map’s required `public` bool does prevent a nameless third state, which is the important structural invariant — but the named admin/rate-limit guarantees are not blocking, contrary to ADR-0005’s “validated at plan time”.
Remediation direction: Move those assertions into `variable "hostnames"` validation (or a resource `precondition`) so plan/apply exit non-zero.
Status: Open

### M2-R1-F05  Low  Operability  Bootstrap SOPS steps are bash-only on a Windows workstation
Location: `docs/runbooks/cluster-bootstrap.md:97-114` (`umask`, `/tmp`, `shred`); `docs/runbooks/secrets.md:60-62` already documents a Windows temp-file path for Terraform vars
Problem: M0 treats Windows as a first-class operator machine. The tunnel-token steps need POSIX `/tmp`, `umask 077`, and `shred`, which Git PowerShell does not provide; Git Bash may lack `shred`. An operator following the runbook on the documented workstation will stall or leave plaintext token files in a temp directory.
Remediation direction: Add a PowerShell equivalent (temp file under `$env:TEMP`, `Remove-Item`) or state that this step is WSL-only, in the same voice as `secrets.md`.
Status: Open

### M2-R1-F06  Low  Operability  Bootstrap verification command is a placeholder
Location: `docs/runbooks/cluster-bootstrap.md:48`
Problem: `talosctl version --nodes "$(talosctl get members -o json | ...)"` is not a runnable command. A first-apply operator cannot copy-paste the verify block.
Remediation direction: Replace with the concrete members/jsonpath invocation already sketched in `cluster-upgrade.md:22`.
Status: Open

### M2-R1-F07  Low  Scalability  Etcd snapshots have no retention
Location: `infra/terraform/hetzner/kubernetes.tf:48-56`; `infra/terraform/hetzner/buckets.tf:22-30`; no lifecycle rule; Hetzner Object Storage lifecycle support is incomplete
Problem: Daily compressed snapshots go forever into a versioned bucket. At this scale it is cheap, but nothing expires failed or ancient dumps, and the teardown runbook treats the bucket as immortal.
Remediation direction: Document a retention policy (console lifecycle or a CronJob prune) once Hetzner’s supported S3 subset is confirmed; do not add an unsupported `aws_s3_bucket_lifecycle_configuration` without an apply test.
Status: Open

### M2-R1-F08  Low  Security  Talos-backup uses the project-wide S3 keys
Location: `infra/terraform/hetzner/kubernetes.tf:50-52`; module `talos_backup.tf:21-32` Secret in `kube-system`
Problem: The in-cluster backup job receives `var.s3_access_key` / `var.s3_secret_key`, which also unlock `ivp-tfstate` and `ivp-cnpg`. Hetzner can scope Object Storage credentials per bucket. Compromising `kube-system` is already severe (the CCM token is there too), but this is extra blast radius that is avoidable.
Remediation direction: Create a dedicated Object Storage credential that can write only `ivp-etcd` and pass that pair to `talos_backup_s3_*`.
Status: Open

## Dimension notes

### Code quality — 8
Two small roots, typed variables with useful validation, documented outputs, camelCase CSI keys matching the module schema, `terraform fmt` / `validate` / `tflint` clean on both, SHA-pinned `terraform.yml` that only validates. Lockfiles are present and not gitignored. Gaps are documentation-and-validation, not spaghetti HCL: check blocks instead of failing validations, the SOPS recipe disagreeing with `secrets.md`, and no `terraform test` assertions.

### Scalability — 8
This is a three-node personal cluster; the shape and the 1–8 worker cap are honest. Cloudflare rate-limit and Access exist at the edge. The only growth leak in scope is unbounded etcd snapshot versions (F07). No N+1, no metric cardinality bomb in this milestone.

### Reliability — 7
Delete protection on servers and buckets, CCM load balancers off, age-encrypted daily etcd snapshots (ahead of the ADR-0004 “CronJob in M3” line), versioning on buckets, firewall limited to two API ports. Single control plane is an accepted ADR-0004 consequence; restore remains M3 and is not scored as missing. The pain is operational reliability of rebuild/destroy (F01) and a rate-limit resource that may refuse to apply (F03).

### Future-proofing and migration readiness — 8
Split Hetzner/Cloudflare roots match ADR-0002; S3 backend examples match ADR-0010; hostnames map and 404 catch-all match ADR-0005; module and toolchain pins match ADR-0004/`versions.env`; Actions are SHA-pinned (ADR-0012); Renovate includes the terraform manager. Provider lock-in is confined to the Cloudflare root and hcloud CCM/CSI, as designed. Weak spot: origin service DNS `cilium-gateway-public.gateway.svc.cluster.local` is a cross-milestone contract with no Gateway object in this repo yet (acceptable for M3, but it is only a variable default).

### Security — 7
API CIDR allow-list, no Hetzner HTTP LB, Access plus origin JWT on admin hostnames, 404 catch-all, sensitive tunnel output, gitignore of state and kubeconfig, CSI LUKS, etcd snapshots encrypted to age. That is a real design, not a checkbox list. It drops from 8 because the in-scope SOPS procedure does not actually engage `.sops.yaml` (F02), the named Access/rate-limit guards are warnings (F04), and backup credentials can read Terraform state (F08).

### Operability — 7
Bootstrap, upgrade, and teardown runbooks exist with preconditions, verify, and rollback sections; `versions.env` lockstep is written down; CI will fmt/validate/tflint on path filter without cloud credentials. A 3 a.m. operator still cannot follow teardown as written (F01), cannot encrypt the tunnel token as written (F02), and hits a bash island on Windows (F05) plus a placeholder talosctl line (F06).

## What was done well
- One `hostnames` map generates CNAME, tunnel ingress, and Access together, with origin JWT (`origin_request.access`) on non-public hosts and a 404 catch-all — that is the ADR-0005 invariant implemented as data flow, not as a comment.
- `firewall_use_current_ipv4` is mutually exclusive with an explicit `firewall_api_source`, and an empty CIDR list is rejected, so the module’s concatenate-with-current-IP behaviour cannot silently open the APIs to both.
- CCM and kube-API load balancers are explicitly off, so ADR-0005 is not left to module defaults.
- Etcd snapshots are age-encrypted into `ivp-etcd` in this milestone, with a required `age1…` variable, which is the correct mitigation for the accepted single-CP failure mode even though the CronJob was scheduled for M3 in ADR-0004.
- `terraform.yml` pins Terraform 1.16.2 and TFLint 0.59.1 by SHA, `permissions: contents: read`, and never applies — CI cannot spend cloud money or mutate the edge.
