## Findings

### M3-R1-F01  High  Reliability  Loki cannot PutObject to Hetzner Object Storage
Location: `kubectl -n loki logs sts/loki -c loki` (repeated `operation error S3: PutObject` HTTP 403 `AccessDenied: UnknownError` from `reporter.go` cluster-seed CAS and `delete_requests_db_boltdb.go`); `k8s/infrastructure/loki/values.yaml:19-53`; live Secret `loki-s3` in namespace `loki` (key names only: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`)
Problem: Loki is Running and Alloy is tailing/pushing, but every observed object-store write is denied. Index shipper logs `uploading tables` with no successful Put logged (startup had 0 local indices). 30-day S3 retention and ADR-0007 object storage therefore do not hold; logs live only on the 10Gi PVC/WAL until rebuild or disk fill. Likely causes: SOPS key pair lacks `s3:PutObject` on `ivp-loki`, or AWS SDK v2 default checksums that Hetzner Ceph rejects as 403 UnknownError.
Remediation direction: Prove PutObject to `ivp-loki` with the same key pair (without committing plaintext). If the keys are valid, set the AWS checksum/env knobs Ceph needs and disable Loki usage reporting; confirm a chunk or index object appears in the bucket, then re-check Loki logs for zero AccessDenied.
Status: Open

### M3-R1-F02  Medium  Security  Argo CD UI exec is enabled
Location: `k8s/bootstrap/argocd/values.yaml:24`; live `argocd-cm` `exec.enabled=true`
Problem: ADR-0006â€™s `--enable-exec` is the Kustomize plugin flag (`kustomize.buildOptions`, also set). `configs.cm.exec.enabled` is a different switch: it turns on the Argo CD pod-exec terminal. Combined with `policy.csv` admin for the operator email, the UI can shell into workloads. That is extra blast radius behind Access, not required for KSOPS.
Remediation direction: Set `exec.enabled` to false unless there is a written need for the UI terminal; keep `kustomize.buildOptions --enable-exec` for KSOPS.
Status: Open

### M3-R1-F03  Medium  Security  k8s-validate CI installs Helm/kustomize/kubeconform without checksums
Location: `.github/workflows/k8s-validate.yml:38-59`; contrast `hygiene.yml:44-53` and `scripts/setup-wsl.sh` helm fetch (checksum-verified)
Problem: ADR-0012 pins Actions by SHA (checkout is pinned) and treats supply chain as a first-class control. This workflow `curl`s GitHub/get.helm.sh tarballs by version pin only. A substituted binary would still `kubeconform` whatever the attacker wants, including a green CI on invalid manifests.
Remediation direction: Verify published SHA256 (as hygiene does for sops and setup-wsl does for helm) before `install`.
Status: Open

### M3-R1-F04  Medium  Reliability  GitOps waves race secrets (and Barman namespace) with their consumers
Location: `k8s/clusters/hetzner/applications/kube-prometheus-stack.yaml` and `kube-prometheus-stack-resources.yaml` both wave `"2"`; `loki.yaml` and `loki-resources.yaml` both wave `"3"`; `barman-cloud.yaml:22-31` destination `cnpg-system` with no `CreateNamespace=true`, same wave as `cnpg-operator.yaml`
Problem: Bootstrap applies secrets then Helm (`docs/runbooks/argocd-bootstrap.md:92-107`), which is why the live cluster came up. After handover, Argo syncs a wave in parallel: Grafana wants `grafana-admin`, Loki pods `extraEnvFrom` `loki-s3`, Barman wants `cnpg-system`. Missing secrets/namespace yield CrashLoop until retry. `prune: true` on `root-application.yaml` targeting GitHub `main` that does not yet contain these paths would delete the live platform if step 4 is applied early.
Remediation direction: Put KSOPS resource Applications (and CNPG namespace) on an earlier wave than the Helm consumers; keep `CreateNamespace=true` on Barman or depend on the operator app. Do not apply `root-application.yaml` until `main` lists the k8s tree.
Status: Open

### M3-R1-F05  Medium  Security  NetworkPolicies are only on gateway and cloudflared
Location: `k8s/README.md:21-22` (every workload gets a NetworkPolicy); policies exist only at `k8s/infrastructure/cloudflared/networkpolicy.yaml` and `k8s/infrastructure/gateway/networkpolicy.yaml`. Hubble/Grafana/Argo/Loki have ClusterIPs and no NP. Loki `auth_enabled: false` (`values.yaml:7`). ADR-0014: Hubble has no app auth.
Problem: Edge Access is real (criterion 4). Inside the cluster, any pod can push/query Loki and load Hubble UI. The gateway NP `podSelector: {}` in namespace `gateway` does not select Cilium Envoy (kube-system), so it does not enforce the origin path either.
Remediation direction: Default-deny in `loki`, `monitoring`, `argocd`, and `kube-system` Hubble; allow Alloyâ†’Loki, Grafanaâ†’Loki/Prometheus, cloudflaredâ†’Gateway Service, and Prometheus scrapes. Treat Hubble as admin-only in-cluster as well as at the edge.
Status: Open

### M3-R1-F06  Medium  Security  Entire `monitoring` namespace is PSA privileged
Location: `k8s/infrastructure/kube-prometheus-stack/resources/namespace.yaml:6-10`
Problem: node-exporter and Alloy filesystem log readers need hostPath; the comment says to constrain via pod securityContext. PSA `enforce: privileged` also admits Grafana, Prometheus, Alertmanager, and the operator. A future or compromised chart default can start a privileged pod in the same namespace without a PSA deny.
Remediation direction: Keep privileged only if a dedicated host-scrape namespace is worse; otherwise split exporters into a host-tools namespace and leave Grafana/Prometheus at `restricted` or `baseline`.
Status: Open

### M3-R1-F07  Low  Reliability  CoreDNS has two replicas and no PDB

Remediation direction: Add a CoreDNS PDB in the module overlay or an Argo resource, minAvailable 1.
Status: Open
