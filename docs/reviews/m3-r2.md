## Findings

### M3-R1-F01  High  Reliability  Loki cannot PutObject to Hetzner Object Storage
Location: `kubectl -n loki logs sts/loki -c loki` (this round: `failed to flush chunks: store put chunk: upload s3 object: Access Denied` and `failed to upload table table=loki_index_20712 err="upload s3 object: Access Denied."`); `k8s/infrastructure/loki/values.yaml:19-77`; live Secret `loki-s3` key names only; pack `docs/reviews/evidence/m3/s3-put-probe.txt` and `loki-s3-logs.txt`
Problem: Round-2 knobs are live (`use_thanos_objstore: true`, `bucket_lookup_type: path`, `AWS_REQUEST_CHECKSUM_CALCULATION=when_required`, `AWS_EC2_METADATA_DISABLED=true`, `analytics.reporting_enabled: false`, helm loki revision 5). Every observed object-store write is still denied. Independent workstation ListObjectsV2 returns 200 and PutObject 403 on `ivp-loki` with the same key pair shape as `terraform.tfvars` `s3_access_key`. 30-day S3 retention and ADR-0007 therefore do not hold; logs live only on the 10Gi PVC/WAL until rebuild or disk fill. This is no longer unexplained Loki config; it is a non-writable object-store credential (or a client Hetzner still rejects the same way Terraform does not).
Remediation direction: In Hetzner Console, give this access key write on `ivp-loki` (and confirm PutObject is not denied by a bucket policy). Prove a `probe/` object appears without committing plaintext, then confirm Loki logs have zero Access Denied and index/chunk prefixes exist in the bucket.
Status: Open

### M3-R1-F06  Medium  Security  Entire `monitoring` namespace is PSA privileged
Location: `k8s/infrastructure/kube-prometheus-stack/resources/namespace.yaml:6-13`
Problem: node-exporter and Alloy filesystem log readers need hostPath. PSA `enforce: privileged` still admits Grafana, Prometheus, Alertmanager, and the operator in the same namespace.
Remediation direction: Keep privileged only if a dedicated host-scrape namespace is worse; otherwise split exporters and leave Grafana/Prometheus at `restricted` or `baseline`.
Status: Accepted (justification: a second host-tools namespace would still be privileged and would split ServiceMonitors/RBAC on a two-worker cluster; the comment now forbids adding new privileged pods. Reasonable for Phase 1.)

### M3-R1-F02  Medium  Security  Argo CD UI exec is enabled
Location: `k8s/bootstrap/argocd/values.yaml:22-25`; live `kubectl -n argocd get cm argocd-cm` `exec.enabled=false`; `kustomize.buildOptions=--enable-alpha-plugins --enable-exec --enable-helm`
Problem: `configs.cm.exec.enabled` was the UI pod-exec terminal, not the KSOPS Kustomize flag.
Remediation direction: Keep `kustomize.buildOptions --enable-exec` for KSOPS; leave UI exec off.
Status: Fixed in round 2

### M3-R1-F03  Medium  Security  k8s-validate CI installs Helm/kustomize/kubeconform without checksums
Location: `.github/workflows/k8s-validate.yml:46-62`; `scripts/versions.env:45-48`
Problem: ADR-0012 treats supply chain as a first-class control. Version-only curl was insufficient.
Remediation direction: Verify published SHA256 before install.
Status: Fixed in round 2 (helm 4.3.0 linux-amd64 checksum `86584a54…` matches the published release; kustomize 5.8.1 and kubeconform 0.8.0 also `sha256sum -c`)

### M3-R1-F04  Medium  Reliability  GitOps waves race secrets (and Barman namespace) with their consumers
Location: `k8s/clusters/hetzner/applications/kube-prometheus-stack-resources.yaml:7` and `loki-resources.yaml:7` wave `"1"`; Helm consumers remain waves 2 and 3; `k8s/clusters/hetzner/applications/barman-cloud.yaml:25-31` now `CreateNamespace=true`

Remediation direction: Keep resource Applications on an earlier wave than Helm consumers; do not apply `root-application.yaml` until `main` lists the k8s tree.
Status: Fixed in round 2 (wave split and Barman `CreateNamespace` done; the root-app prune hazard remains an operator step, not an open finding)

### M3-R1-F05  Medium  Security  NetworkPolicies are only on gateway and cloudflared
Location: live `kubectl get netpol -A` (argocd, cloudflared, gateway, kube-system/hubble-ui-from-gateway, loki, monitoring); `k8s/infrastructure/loki/resources/networkpolicy.yaml`; `k8s/infrastructure/kube-prometheus-stack/resources/networkpolicy.yaml`; `k8s/infrastructure/gateway/kube-system.yaml:1-23`

Remediation direction: Default-deny in loki, monitoring, and Hubble; allow Alloy→Loki, Grafana→Loki/Prometheus, cloudflared→Gateway, Prometheus scrapes.
Status: Fixed in round 2 (Loki ingress 3100/9095 from monitoring only; monitoring ingress from monitoring/gateway/kube-system; Hubble ingress from gateway namespace, which is also where `cilium-gateway-public` CiliumEnvoyConfig lives. Residual chart allow-all on `argocd-server` is M3-R2-F05.)
