## Findings

### M4-R1-F01  High  Reliability  Two replicas run unlocked goose.Up on every start
Location: `apps/notebook-api/internal/migrate/migrate.go:22-39`; `apps/notebook-api/cmd/notebook-api/main.go:45-48`; `k8s/apps/notebook-api/base/deployment.yaml:9`
Problem: Round 1: `goose.UpContext` (no session locker) on Deployment replicas=2 raced `CREATE TABLE` on first apply. Round 2 wraps `goose.UpContext` with `SELECT pg_advisory_lock($1)` / unlock on a short-lived `sql.Open` handle that `UpURL` closes. Session locks are connection-scoped; because the handle is closed after migrate, the lock is held (on an idle pooled conn) until `Close()` and the other replica waits. That serializes first boot. Residual: the lock is not pinned to `db.Conn()` (see M4-R2-F01).
Remediation direction: Already addressed for the outage mode. Pin the lock to one connection (or a migrate Job) so it does not depend on `Close()`.
Status: Fixed in round 2

### M4-R1-F02  Medium  Reliability  20 MiB item cap is not the wire limit the API enforces
Location: `apps/notebook-api/internal/api/http.go:27-32,171,194-196`; `apps/notebook-api/internal/api/http_test.go:241-264`

### M4-R2-F01  Low  Reliability  Advisory lock is not pinned to one SQL connection
Location: `apps/notebook-api/internal/migrate/migrate.go:13-39` (`sql.Open` pool, then `ExecContext` lock, then `goose.UpContext` on the same `*sql.DB`)
Problem: `pg_advisory_lock` is session-scoped. `database/sql` returns the conn to the pool after the lock `Exec`, so goose runs on a different session and `pg_advisory_unlock` may no-op on a third. Today this still serializes two replicas because `UpURL` `defer db.Close()` drops the locked idle conn. If migrate is later wired to a long-lived pool, F01’s race returns without a test noticing (`internal/migrate` coverage 0.0%).
Remediation direction: `db.Conn(ctx)` (or goose `WithSessionLocker`) so lock, migrate, and unlock share one session; add a comment that Close is not the lock protocol.
Status: Open

### M4-R2-F02  Low  Code quality  Island allows 20 MiB files that cannot fit the ciphertext cap
Location: `apps/web/src/components/islands/Notes.tsx:97-117`; `apps/notebook-api/internal/api/http.go:194-196`
Problem: Images are `btoa`’d into the envelope, then AES-GCM’d; the server caps `len(ct)` at 20 MiB. A file just under `20 * 1024 * 1024` becomes ~27 MiB ciphertext and 413s after the user waited on Argon2id. The server cap is correct; the UI oversells file size.
Remediation direction: Gate `file.size` at ~14 MiB (or store raw bytes in the envelope) so a file the UI accepts survives `MaxItemBytes`.
Status: Open
