## Findings

### M5-R1-F01  High  Reliability  LokiNotReady would not have fired on the M3 Access Denied outage
Location: `k8s/infrastructure/kube-prometheus-stack/resources/platform-alerts.yaml:95-103`; `docs/runbooks/incidents.md:112-123`; live M3 evidence `docs/reviews/m3-r2.md:22,40-42` (`loki-0` 1/1 Ready while `upload s3 object: Access Denied`); M3-R3 close-out `docs/reviews/m3-r3.md:42` (“Alert on Loki Access Denied in Milestone 5”); Loki ServiceMonitor already enabled (`k8s/infrastructure/loki/values.yaml:114-124`)
Problem: The rule is `kube_statefulset_status_replicas_ready{namespace="loki",statefulset="loki"} < 1` for 10m. That matches ADR-0007’s “alert if the single Loki pod restarts.” It does not match the failure that actually voided 30-day retention: Hetzner Ceph 403 on PutObject while the StatefulSet stayed Ready. The runbook only greps AccessDenied *after* the pod is already unready. `check-alerts.sh` is green because a heading exists. Object-store error metrics from the Loki chart ServiceMonitor are unused.
Remediation direction: Add a rule on Loki/thanos object-store failures (or a log-derived AccessDenied rate) that pages while the pod is still Ready, and keep LokiNotReady for the crash/restart case. Prove it against the M3 log signature, not against a killed pod.
Status: Open

### M5-R1-F02  Medium  Reliability  CertificateExpiring cannot fire as written, and the runbook names the wrong namespace
Location: `platform-alerts.yaml:64-67`; PromQL `and` requires identical label sets; `certmanager_certificate_ready_status` carries `condition` and `certmanager_certificate_expiration_timestamp_seconds` does not, so the `and` is empty. Certificate lives in `cert-manager` (`k8s/infrastructure/cert-manager-issuers/certificate.yaml:7-8`); runbook says `-n gateway` (`docs/runbooks/incidents.md:91`). No cert-manager ServiceMonitor/PodMonitor exists under `k8s/` (repo grep).
Problem: The only in-repo certificate-expiry alert is dead PromQL. Even if rewritten, this repo never scrapes cert-manager. Public TLS terminates at Cloudflare (ADR-0005), so this is not an edge-TLS outage, but the M5 criterion asked for a certificate-expiry alert and the 3 a.m. section points at a Certificate that is not in `gateway`.
Remediation direction: Join with `on(namespace, name)` (or `ignoring(condition)`), scrape cert-manager, and point the runbook at `cert-manager/wildcard-ivanpanev-net`.
Status: Open

### M5-R1-F03  Medium  Reliability  Restore drill copies write-capable live S3 credentials onto the live WAL prefix with no mechanical WAL-archiver guard
Location: `scripts/restore-drill.sh:17-27` (copies `notebook/cnpg-s3` into `notebook-restore`); `k8s/apps/notebook-restore/objectstore.yaml:10` `destinationPath: s3://ivp-cnpg/notebook`; restore Cluster has no `spec.plugins` (`cluster.yaml:1-42`) while production sets `isWALArchiver: true` (`k8s/apps/notebook-api/base/cluster.yaml:17-21`); `scripts/k8s-validate.sh:93` kubeconforms the overlay but never asserts the archiver is absent; restore NetworkPolicy allows egress TCP/443 (`networkpolicy.yaml:26-28`)
Problem: The intended control is omission of `isWALArchiver`, which is the right CNPG switch and is documented (`objectstore.yaml:1-2`, `restore-drill.md:5-6,65`). Omission is not the same as `isWALArchiver: false`, is not CI-enforced, and the scratch Cluster is given the production PutObject key to the production prefix. A one-line plugin addition, or a future operator default that archives when an ObjectStore exists, writes WAL into live `serverName: notebook`. The script’s awk rewrite also leaves `managedFields` / Argo tracking annotations (unlike the runbook’s Python metadata rewrite at `restore-drill.md:51-54`), so `kubectl apply` of the copied Secret is the fragile path the operator is told to run.
Remediation direction: Copy a list/get-only key (or mint a restore-only pair), set `spec.plugins[].isWALArchiver: false` explicitly, and fail `k8s-validate.sh` / `check-alerts.sh` if `notebook-restore` ever contains `isWALArchiver: true`. Strip Secret metadata to name+namespace like the runbook’s Python path.
Status: Open

### M5-R1-F04  Medium  Reliability  CNPG alerts watch nightly backups, not WAL archiving, so RPO can silently become hours
Location: `platform-alerts.yaml:35-48` (`barman_cloud_cloudnative_pg_io_last_available_backup_timestamp` / `last_failed_backup_timestamp`); `k8s/apps/notebook-api/base/scheduledbackup.yaml:7` `0 0 2 * * *`; ADR-0008 continuous WAL; ADR-0004 RPO “bounded by CNPG WAL archiving (minutes)”
Problem: `CNPGBackupMissing` allows 36h after the last successful *base* backup. WAL archive_command can be stuck for a full night plus the 36h window while those gauges stay healthy. A restore drill or home-cluster recovery would then lose every write since the last nightly, which is not the RPO the ADRs recorded. Plugin 0.8.0 does export the backup-timestamp metrics (changelog #459/#467); they are the right names for backups, not a substitute for archive lag.
Remediation direction: Alert when last archived WAL (plugin or `pg_stat_archiver`) is older than a few minutes on a cluster with `isWALArchiver: true`, in addition to the 36h base-backup gap.
Status: Open

### M5-R1-F05  Low  Operability  notebook-api Grafana dashboard has no latency panel the latency runbook tells you to use
Location: `k8s/infrastructure/kube-prometheus-stack/resources/dashboard-notebook-api.yaml:1-42` (request rate and 5xx only); `docs/runbooks/incidents.md:106-110` (“same dashboard” for NotebookAPILatency)
Problem: On-call is sent to dashboard uid `notebook-api` for p99 > 2s with no p99 panel and no histogram query. The alert PromQL itself (`platform-alerts.yaml:83-88`) is fine (`sum by (le)` on `http_request_duration_seconds_bucket`, labels `code` match `metrics.go:13-27`).
Remediation direction: Add a p99 panel using the same expr as the alert.
Status: Open

### M5-R1-F06  Low  Future-proofing  Restore Cluster floats `postgresql:18`, same unpinned tag as live (M4-R1-F11 now on the restore path)
Location: `k8s/apps/notebook-restore/cluster.yaml:8`; `k8s/apps/notebook-api/base/cluster.yaml:8`; BACKLOG `M4-R1-F11`
Problem: A restore after a catalog republish can recover onto a different `:18` digest than the backup. CNPG will often accept a newer minor and refuse an older one; either way the drill is no longer a like-for-like of production. This was Low for M4; it is now the image the restore runbook will actually boot.
Remediation direction: Pin restore and live to the same digest (or image catalog) before the first drill.
Status: Open

### M5-R1-F07  Nit  Operability  Cost inventory labels Alertmanager’s PVC as Grafana
Location: `docs/cost.md:18` “Grafana 2Gi”; `kube-prometheus-stack/values.yaml:97-104` Alertmanager 2Gi; Grafana stanza has no persistence (`values.yaml:106-159`); Loki 10Gi and Prometheus 20Gi and notebook 10Gi match
Problem: The euro total is still ~42Gi at €0.0476/GiB, so the projection is not wrong on cost. The Actual-column paste will not line up with a Grafana volume that does not exist.
Remediation direction: Name Alertmanager 2Gi and drop the Grafana PVC line until Grafana persistence is enabled.
Status: Open

## Dimension notes

### Code quality — 8
Restore and alerts are small, named for their job, and wired into `k8s-validate.sh` / `check-alerts.sh`. Barman metric names are the plugin gauges, not the stale `cnpg_collector_*` zeros. The mechanical alert check is heading-and-annotation only, which is why F02 is green in CI. `restore-drill.sh` awk is a worse Secret clone than the runbook’s Python rewrite. Dashboard JSON is two panels. No dead Report-Only CSP path. This is solid milestone code with testable holes, not a mess.

### Scalability — 8
Phase 1 load does not stress these artifacts. PVCNearFull is a ratio per volume; NodePressure is per node; notebook-api histograms aggregate `sum by (le)` rather than exploding per instance. Restore adds one 10Gi PVC and is documented as a cost leak if left behind (`docs/cost.md:30`). CNPGBackupMissing’s 36h window is coarse (F04), not a cardinality problem. Fine at 10× this cluster; 100× is a later Prometheus/Loki retention discussion already accepted in ADR-0007.

### Reliability — 6
The happy-path rules (node, PVC, cloudflared replicas, notebook 5xx/p99, CNPG backup timestamps) are plausible and will load (`ruleSelectorNilUsesHelmValues: false`). The two rules that exist because of prior production pain do not work: LokiNotReady misses Access Denied while Ready (F01), CertificateExpiring is empty PromQL (F02). Restore will not archive WAL *as committed*, but the drill runs with live PutObject keys on the live prefix and no CI lock (F03). WAL lag is unalerted (F04). That is happy-path monitoring, not the failure modes this cluster has already had.

### Future-proofing and migration readiness — 8
No ADR deviation. Restore is deliberately not in `k8s/clusters/hetzner`. ObjectStore endpoint/bucket are configuration in the same shape as production (ADR-0008/0010). Migration checklist reds are only home-cluster items. Threat model records write-to-`main` ≡ cluster-admin via KSOPS `--enable-exec` (ADR-0006). Overlay still deploys `:main` until first CI digest (yellow #7, already in the threat model). Unpinned `postgresql:18` on the restore Cluster is the leftover that now sits on the migration path (F06).

### Security — 8
CSP is enforce on both channels: per-page hash meta plus `_headers` `frame-ancestors 'none'`. `check-dist.mjs` will demand `security.txt.asc` once `publickey.asc` exists. Threat model is specific (PAB, Loki versioning, KSOPS exec, project-wide S3 keys from BACKLOG M2-R1-F08). Restore overlay is not GitOps-synced, which is the correct control against a second writer. The copied production S3 secret into `notebook-restore` is the remaining loaded gun (F03), not an exposure on the public site.

### Operability — 7
`incidents.md` is one section per platform alert with concrete kubectl and a ntfy/silence policy. Restore runbook has preconditions, verify, teardown, and “do not delete `s3://ivp-cnpg/notebook`.” Cost and architecture are written for a stranger. What fails at 3 a.m. is following those docs into a dead Certificate query in the wrong namespace (F02), a Loki AccessDenied grep that only runs after the pod is down (F01), and a latency runbook that points at a dashboard with no latency panel (F05). `check-alerts.sh` will not catch any of that.

## What was done well
- Restore is a manual overlay with three independent “do not GitOps this” comments (`k8s/apps/notebook-restore/kustomization.yaml:3-5`, `k8s/README.md:27-29`, `restore-drill.md:8-9`), and `k8s/clusters/hetzner` does not reference it. That is the correct shape for a WAL-sharing prefix.
- CNPG backup alerts use `barman_cloud_cloudnative_pg_io_*` and the comment explains why `cnpg_collector_*` stays 0 (`platform-alerts.yaml:1-2,35-48`); plugin 0.8.0 is the version that added those metrics.
- Prometheus will actually select the extra rules: `ruleSelectorNilUsesHelmValues: false` (`values.yaml:55-57`) avoids the default `release:` label footgun.
- `check-alerts.sh` is a real gate (`k8s-validate.sh:15` plus `k8s-validate.yml`), not a README promise; re-run matched the pack (9 alerts, 9 headings).
- CSP is designed around per-page hashes: enforce meta + a tiny `_headers` policy for `frame-ancestors`, with an explicit reason Report-Only cannot substitute (`_headers:1-5`, `astro.config.ts:68-71`).
- Platform threat model states the KSOPS `--enable-exec` trust boundary in the same words as ADR-0006 (`platform-threat-model.md:28-31`) and forbids recreating PublicAccessBlock / enabling Loki versioning (`:35-37,47-48`).
- Migration checklist marks restore and digest as Yellow, not Green, until `main` and a backup exist (`migration-readiness.md:11-16,22-24`).
