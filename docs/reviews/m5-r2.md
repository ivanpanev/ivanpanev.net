## Findings

### M5-R1-F01  High  Reliability  LokiObjectStoreErrors still would not have fired on the M3 Access Denied outage
Location: `k8s/infrastructure/kube-prometheus-stack/resources/platform-alerts.yaml:118-128`; `k8s/infrastructure/loki/values.yaml:32-34` (`use_thanos_objstore: true`); Grafana Loki docs “Object store operations” name `loki_objstore_bucket_operation_failures_total` / `loki_objstore_bucket_operations_total` (not `thanos_objstore_*` or `loki_s3_*`); M3 evidence `docs/reviews/m3-r2.md:22,40-42` (`loki-0` 1/1 Ready, `upload s3 object: Access Denied`); Loki ServiceMonitor already enabled (`loki/values.yaml:114-124`)
Problem: Round 2 added `LokiObjectStoreErrors` as `rate(loki_s3_request_duration_seconds_count{status_code=~"403|5.."}) or rate(thanos_objstore_bucket_operation_failures_total{namespace="loki"}) or push-route 5xx`. This cluster’s working S3 path is the Thanos client (the M3 Ceph workaround). Grafana documents that path as `loki_objstore_*`. `loki_s3_*` is the unused native AWS client; `thanos_objstore_*` is the unwrapped library name Loki does not export. The third clause is distributor/push 5xx; the M3 failure flushed chunks in the background while the StatefulSet stayed Ready and ingest still answered. `or` of three empty series is empty. `check-alerts.sh` is green because a heading exists. The runbook now greps AccessDenied while Ready (`incidents.md:141-156`); the rule that should page that runbook does not.
Remediation direction: Alert on `loki_objstore_bucket_operation_failures_total` (optionally `operation="upload"`) or a log-derived AccessDenied rate, keep LokiNotReady for the crash case, and prove the series exists while `sts/loki` is Ready against the M3 log signature.
Status: Open

### M5-R1-F03  Medium  Reliability  Restore `isWALArchiver: false` is a CI string, not a runtime WAL guard
Location: `k8s/apps/notebook-restore/cluster.yaml:18-20` (plugin enabled, `isWALArchiver: false`, no `serverName` override on the local plugin); `objectstore.yaml:10` `destinationPath: s3://ivp-cnpg/notebook`; `scripts/k8s-validate.sh:17-24` greps YAML only; `scripts/restore-drill.sh:17-40` still copies `notebook/cnpg-s3` (PutObject) into `notebook-restore`; CNPG 1.30 `internal/cnpi/plugin/client/wal.go` `innerArchiveWAL` invokes every plugin advertising `WAL_ARCHIVE` and does not read `isWALArchiver`; plugin-barman-cloud#797 still Open (2026-04-29); no `cnpg.io/skipWalArchiving` on the restore Cluster
Problem: Round 1 omitted `spec.plugins`, which is one of the two cases upstream says will not archive via plugin. Round 2 added the Barman plugin so the flag could be set to `false` and grepped. CNPG 1.30 still calls `ArchiveWAL` on every WAL-capable enabled plugin; `GetEnabledWALArchivePluginName()` returning empty only skips the *legacy* in-tree path, which this overlay never had. After the scratch cluster promotes, archive_command can PutObject into `s3://ivp-cnpg/notebook/<serverName>/` with the live write key. Default `serverName` is the Cluster name `notebook-restore`, so live `serverName: notebook` objects are probably not overwritten — that is luck, not the control the runbook claims (`restore-drill.md:4-6,65`). `objectstore.yaml:1-2` still says the flag is omitted. List-only key remains unminted.
Remediation direction: Disable WAL on the scratch cluster with `cnpg.io/skipWalArchiving: enabled` (and/or a restore-only destinationPath), copy a list/get-only key, and treat `isWALArchiver: false` as documentation at best. CI should fail on a missing skip annotation or on a write-capable secret copy, not only on the string `true`.
Status: Open

### M5-R1-F04  Medium  Reliability  CNPGWALArchivingStuck watches a metric CNPG 1.30 does not export
Location: `platform-alerts.yaml:1-2,78-87` (`cnpg_collector_pg_stat_archiver_last_archived_time > 0` and `time() - … > 900`); CNPG 1.30 `config/manager/default-monitoring.yaml` query name `pg_stat_archiver`, column `last_archived_time`; CNPG 1.30 `docs/src/monitoring.md` collector sample lists `cnpg_collector_pg_wal_archive_status` and user-defined examples `cnpg_pg_replication_*`, not `cnpg_collector_pg_stat_archiver_*`
Problem: Query metrics are `cnpg_<query>_<column>` → `cnpg_pg_stat_archiver_last_archived_time` (and `cnpg_pg_stat_archiver_seconds_since_last_archival`). The Go collector prefix `cnpg_collector_*` is the set the file header correctly says stays at 0 for plugin backups; it never grew a `pg_stat_archiver_last_archived_time` child. `> 0` on a missing series is empty PromQL — the same hole as round-1 CertificateExpiring. Nightly `barman_cloud_*` backup rules (`:35-54`) can stay green while WAL has been stuck for hours, which is the ADR-0004 RPO the rule was added to protect. `cnpg_collector_pg_wal_archive_status{value="ready"}` is the collector gauge that would actually show a stuck archive_command queue.
Remediation direction: Alert on `cnpg_pg_stat_archiver_seconds_since_last_archival` (or `last_archived_time`) and/or `cnpg_collector_pg_wal_archive_status{value="ready"}`, restricted to clusters with `isWALArchiver: true`.
Status: Open

## Dimension notes

### Code quality — 7
Restore, alerts, and gates are still small and named for their job. Secret clone is now an explicit `apiVersion/kind/metadata/data` rewrite (`restore-drill.sh:29-38`), which is the right shape. What dropped the score is repeating round-1’s failure mode: `check-alerts.sh` remains heading-and-annotation only, so `LokiObjectStoreErrors` and `CNPGWALArchivingStuck` are CI-green dead PromQL. The overlay comment in `objectstore.yaml` disagrees with the Cluster spec next to it. No new dead Report-Only CSP path.

### Scalability — 8
Phase 1 load does not stress these artifacts. PVCNearFull is a ratio per volume; NodePressure is per node; notebook-api histograms still `sum by (le)`. Restore adds one 10Gi PVC and is still documented as a cost leak if left behind (`docs/cost.md:30`). Cardinality of the new Loki/WAL rules is one cluster / one Loki job. Fine at 10×; 100× remains the ADR-0007 Prometheus/Loki retention discussion.

### Reliability — 6
CertificateExpiring can now match (`on(namespace, name)`) and has a scrape (`servicemonitor-cert-manager.yaml`) that Prometheus will select (`serviceMonitorSelectorNilUsesHelmValues: false`). Node, PVC, cloudflared, notebook 5xx/p99, and plugin backup timestamps remain plausible. The two rules this milestone owed to prior production pain still do not work: Loki object-store 403 while Ready (F01) and WAL lag (F04). Restore’s YAML flag is not what CNPG 1.30 uses to skip plugin archive (F03). That is still happy-path monitoring plus a paper WAL guard.

### Future-proofing and migration readiness — 8
No ADR deviation. Restore is still not in `k8s/clusters/hetzner`. ObjectStore endpoint/bucket stay configuration (ADR-0008/0010). Migration reds are only home-cluster items. Threat model still records write-to-`main` ≡ cluster-admin via KSOPS `--enable-exec` (ADR-0006). Overlay still deploys `:main` until first CI digest (yellow #7). Unpinned `postgresql:18` on the restore Cluster is unchanged (F06).

### Security — 8
CSP is still enforce on both channels. `check-dist.mjs` will demand `security.txt.asc` once `publickey.asc` exists. Threat model is specific on PAB, Loki versioning, and KSOPS exec. Restore overlay is not GitOps-synced. The remaining loaded gun is the copied production S3 secret into a Cluster whose plugin will accept ArchiveWAL RPCs (F03), not an exposure on the public site.

### Operability — 7
`incidents.md` now has the right Certificate namespace, a LokiObjectStoreErrors section that greps AccessDenied while Ready, and a WAL-stuck section that tells you not to wait for 02:00. Restore runbook checks `isWALArchiver: false` after apply. Cost names Alertmanager. What still fails at 3 a.m. is following those docs into a Loki rule that never pages (F01), a WAL rule that never pages (F04), a threat-model row that sends you to LokiNotReady (M5-R2-F01), and a restore comment that describes a control the operator does not have (F03). `check-alerts.sh` will not catch any of that.
