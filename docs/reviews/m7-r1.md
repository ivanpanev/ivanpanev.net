## Verdict

Overall: 6 — FAIL
Code quality: 7 | Scalability: 6 | Reliability: 6 | Future-proofing: 7 | Security: 6 | Operability: 7

The platform is genuinely live and the GitOps hand-over is real: `main` is the source of truth for 15 Argo CD Applications, the notes API is reachable through Tunnel → Gateway → Envoy → pod with correct CORS, the image running in the cluster is the digest that CI signed and committed, and production serves byte-identical bundles to a local build of HEAD. The single most important problem is that the headline symptom is not fixed: the Cloudflare rate-limit rule (10 requests per 10 s per IP on `/v1/*`) counts CORS preflights, and Cloudflare's 429 carries no `Access-Control-Allow-Origin`, so a normal browser session (open, store, reopen, view, delete: ~14 requests) trips it and the island shows exactly "Failed to fetch" again — I reproduced it in one run. Second, ADR-0012 says `main` is protected and commits are signed; `main` is unprotected, every commit is unsigned, CI pushes to `main` with `GITHUB_TOKEN`, and Argo CD auto-syncs `main` with prune/selfHeal, so a push to `main` is cluster-admin. Recording the IP-locked-token blockers was adequate for the token itself, but the document that caused the mistake (`docs/toolchain.md` prescribing one broad token for Terraform, wrangler, and by extension cert-manager) is unchanged. What moves this to a 9: fix the rate-limit rule and client 429 handling, reconcile ADR-0012 with the CI push design (ruleset with a bypass or a dedicated identity, plus signature verification), publish a per-consumer Cloudflare token inventory, suspend the unused wildcard Certificate until a proper token exists, and turn the HTTPRoute ↔ CNP invariant into a CI check.

## Findings

### M7-R1-F01  High  Reliability  Cloudflare rate limit counts preflights and its 429 has no CORS headers: "Failed to fetch" still reproduces
Location: `infra/terraform/cloudflare/variables.tf:92-101` (`rate_limit_requests = 10`, `rate_limit_period = 10`); `infra/terraform/cloudflare/rate_limit.tf:17-22` (expression `starts_with(http.request.uri.path, "/v1/")`, no method filter, `characteristics ip.src`); `apps/web/src/lib/notebook.ts:142,150` (`fetch` → `throw new Error(...)`, no 429 / `Retry-After` handling); `apps/web/src/components/islands/Notes.tsx:60-61,90-91,149-150` (`setError(e.message)` → literally "Failed to fetch"); `docs/security/notebook-threat-model.md:24,48-50`.
Problem: Every API call from the island carries `X-Auth`, so every distinct URL costs a preflight plus the request. Open notebook = 4 requests, store = 2, view each item = 2, delete = 2. Reopening in a second tab or from a fresh context repeats the preflights. I hit the limit on the 14th request of a single-user session: burst test shows `204 ×10` then `429 ×4`, and the 429 carries only `Retry-After: 10` — no `Access-Control-Allow-Origin` — so the browser reports a CORS failure and `fetch` rejects with `TypeError: Failed to fetch`, which the island prints verbatim. This is the exact symptom M7 exists to fix, and it is worse behind CGNAT/office NAT where `ip.src` is shared. The client has no retry, backoff or user-readable 429 message (BACKLOG M4-R2-F03, now promoted into this finding).
Remediation direction: Exclude `OPTIONS` from the rate-limit expression (preflights carry no auth attempt, so the threat-model guess rate is unchanged) and raise `rate_limit_requests` to a value the UI's own traffic pattern fits (the application token bucket at 2 rps/burst 20 remains the binding limit for guessing); update `notebook-threat-model.md:24` accordingly. In `notebook.ts`, treat a network-level failure and a 429 as "the service is throttling you, retry in N s" with one bounded retry honouring `Retry-After`. Add the burst case to the Playwright notes spec.
Status: Open

### M7-R1-F02  High  Security  ADR-0012 deviation: `main` unprotected and unsigned while CI writes to it and Argo CD auto-syncs it with cluster-admin
Location: `docs/adr/0012-monorepo-ci-and-supply-chain.md:27-28` ("Commits are signed … `main` is protected and requires the validation workflows"); `GET /repos/ivanpanev/ivanpanev.net/branches/main` → `"protected": false`; `git log --format=%G?` → `N` for all 21 commits on `main`; `.github/workflows/notebook-api.yml:81-85,139-157` (`contents: write`, `git push origin HEAD:main` with `GITHUB_TOKEN`); `k8s/clusters/hetzner/root-application.yaml:17-22` (`automated: prune/selfHeal`, `ServerSideApply`); `docs/reviews/BACKLOG.md:35` (the `bedbc29` version of item (d) — "confirm branch protection allows `github-actions[bot]` before enabling it" — was dropped in `b43b43c`).
Problem: The repository is public and is the control plane for the cluster: whatever lands on `main` is applied within `timeout.reconciliation: 180s` by a cluster-admin Argo CD, with prune. Today anything that can push to `main` — the operator's GitHub account, or a compromised third-party step in the `image` job that runs with `contents: write` (six actions plus `go run …@version` for govulncheck in the same workflow) — controls the cluster. ADR-0012's mitigations (protected `main`, required checks, signed commits) are the accepted design and none exists; there is no superseding ADR, and the only note that would have reminded the operator was deleted from the backlog in the last commit. SHA-pinned actions reduce but do not remove the risk.
Remediation direction: Decide and record in ADR-0012 how the bump commit coexists with protection: a GitHub ruleset on `main` requiring `hygiene`/`k8s-validate`/`notebook-api` with a bypass for the Actions app, or a dedicated GitHub App / deploy key identity for the bump, or the bump as an auto-merged PR. Enable signed commits (SSH signing is a one-line git config) and configure Argo CD `signatureKeys` on the project so unsigned commits are not synced. Put the operator steps back in the BACKLOG and in `docs/runbooks/argocd-bootstrap.md` "Preconditions".
Status: Open

### M7-R1-F03  Medium  Security  One broad, IP-locked personal token shared by Terraform, CI deploy and cert-manager; the docs that caused it are unchanged
Location: `docs/toolchain.md:52-54` (one "Cloudflare API token" row for Terraform and wrangler with Zone DNS Edit, Zone Settings Edit, Workers Scripts Edit, Access Apps and Policies Edit, Tunnel Edit, Email Routing); `.github/workflows/web.yml:11-13` and `apps/web/README.md:61` ("Workers Scripts: Edit, Account Settings: Read"); `docs/reviews/BACKLOG.md:35` (d) (adds Workers Routes Edit + Zone Read); `docs/runbooks/argocd-bootstrap.md:169-176` (DNS-01 scopes); `web.yml:11-13` also claims the token is "stored as repository secrets, exposed only … through the `production`/`preview` environments", which is contradictory (a repository secret is available to every non-fork job).
Problem: The evidence says the token in the GitHub environments and in `cloudflare-api-token.secret.yaml` is the operator's account token — the same one `toolchain.md` tells the operator to mint for Terraform, i.e. one carrying Access-policy and Tunnel edit rights. Sitting in CI and in a cluster Secret, that token would let a CI or `cert-manager`-namespace compromise rewrite the Access policies that ADR-0005 relies on to protect argocd/grafana/hubble. The IP lock currently neutralises misuse by accident, and is also why two systems are down. The BACKLOG entry tells the operator what to mint, but four documents give four different scope lists and the canonical one still says "one token".
Remediation direction: Add a single token inventory (in `docs/runbooks/secrets.md` or `toolchain.md`) with one row per consumer — Terraform cloudflare root, `web.yml` deploy, cert-manager DNS-01 — giving exact scopes, zone/account restriction, and the rule that CI and cluster consumers must have no `request_ip` condition; make `web.yml`, `apps/web/README.md` and the BACKLOG point at it instead of repeating scopes. Remove any repo-level copies of the secrets so only the environments hold them.
Status: Open

### M7-R1-F04  Medium  Reliability  Unused wildcard Certificate retries DNS-01 for 13 h with the operator's shared token until Cloudflare throttles that token
Location: `k8s/infrastructure/cert-manager-issuers/certificate.yaml:7-10` (`wildcard-ivanpanev-net`, secret `wildcard-ivanpanev-net-tls`; no Gateway listener, HTTPRoute or other resource references the secret — `git grep wildcard-ivanpanev-net` finds only this file); `cert-manager-live.txt:11-13` and live: challenge `pending`, reason `10502: Too many authentication failures. Please try again later.`
Problem: The certificate serves nothing today (TLS terminates at Cloudflare, ADR-0005:41-44), yet cert-manager keeps presenting a token that Cloudflare rejects, and has now driven the token into Cloudflare's authentication-failure throttling. Because it is the same token the operator uses for Terraform (F03), a `terraform apply` from the operator's machine can fail with 10502 for no visible reason. It also leaves `cert-manager-issuers` permanently Progressing, which trains the operator to ignore a red Application.
Remediation direction: Until a dedicated DNS-01 token exists, either remove the Certificate from the tree (keep the ClusterIssuer) or add it behind a kustomize component that is only enabled when the secret is known-good; document in the runbook that a stuck Challenge must be deleted, not left to retry, when the failure is an auth error.
Status: Open

### M7-R1-F05  Medium  Operability  HTTPRoute ↔ cloudflared CNP ↔ backend CNP is a three-place manual invariant with no check, and ADR-0005's consequence is now stale
Location: `k8s/infrastructure/cloudflared/ciliumnetworkpolicy.yaml:10-13` ("Every HTTPRoute backend … must be listed here"); `k8s/infrastructure/gateway/backend-ingress-entity.yaml:5-8`; `docs/runbooks/argocd-bootstrap.md:160-163` ("Add a rule there whenever `httproutes.yaml` gains a backend"); `scripts/k8s-validate.sh` (no cross-check); `docs/adr/0005-cloudflare-tunnel-only-ingress.md:70-71` ("Adding a hostname is a one-entry change in Terraform plus an `HTTPRoute`; forgetting either produces a 404, never an exposure").
Problem: Adding a hostname now takes four edits (Terraform, HTTPRoute, cloudflared `toEndpoints` with the pod labels and container port, backend `fromEntities: [ingress]`), and forgetting the last two produces a 403 from Envoy that only Hubble explains. The pod labels and container ports are copied from Helm chart internals (`app.kubernetes.io/instance: kube-prometheus-stack`, `k8s-app: hubble-ui`, port 3000/8081/9000) and will drift silently on a chart rename. Today all five match (verified live), but nothing in CI keeps it that way. ADR-0005's "one entry + one HTTPRoute" consequence is no longer true and should carry a revision line.
Remediation direction: Add a step to `scripts/k8s-validate.sh` that renders `httproutes.yaml`, extracts `backendRefs` (namespace, service) and asserts a matching `toEndpoints` entry in the cloudflared CNP and a `fromEntities: [ingress]` CNP for the same selector; record the four-step procedure and the 403 symptom as an ADR-0005 revision.
Status: Open

## Dimension notes

### Code quality — 7
The CI fixes are competent and each commit says why (`d6c958d`, `2bffe12`, `5cf81bc`): gitleaks moved from an action that needs `github.event.before` to a checksum-verified pinned CLI over full history; the kustomize download is extracted outside the checkout; the golangci fixes (`httptest.NewRequestWithContext`) are mechanical and correct. `pnpm test` (135), `pnpm check`, `pnpm build`, `lint:html` all pass locally; `notebook-api` CI passed on `5cf81bc`. Deductions: the evidence script stops one click short of proving the round-trip (F06), the kustomize checksum is duplicated (F07), a dead NetworkPolicy rule sits beside a comment explaining it is dead (F09), and I could not run Go locally, so the Go tests remain CI-only from my side.

### Scalability — 6
This is a three-node personal platform and the manifests are sized honestly, but the one edge control that scales with users — the rate-limit rule — fails at N = 1 (F01). A shared NAT of a handful of users or one user browsing a notebook with ten items will be throttled, and the failure is indistinguishable from an outage in the UI. Nothing else in M7 changes load characteristics; the 2-replica API and single CNPG instance are the M4 design.

### Reliability — 6
The data path is verified end to end and the digest-pinned image, digest-bumped overlay and running pod agree. Cilium identity handling (`kube-apiserver`, `ingress` entities) was diagnosed with Hubble and fixed at the right layer. Against that: the headline defect still reproduces (F01); an unused Certificate is retrying itself into Cloudflare auth throttling with the operator's shared token (F04); the HTTPRoute↔CNP invariant is manual and will produce a Hubble-only 403 the first time someone forgets it (F05); `cert-manager-issuers` is permanently Progressing. The `web.yml` deploy path is red, so the next content change will not ship until the operator acts.

### Future-proofing and migration readiness — 7
Pins are current and SHA-referenced; the SSA-default spelling keeps Git equal to live without `ignoreDifferences`, which is the better long-term choice. The CNPs are Cilium-specific by necessity and are clearly labelled as such, next to the portable NetworkPolicies, so a non-Cilium cluster loses only the Envoy-identity rules. Deductions: ADR-0012 is contradicted by the live repository state and by the CI push design without a superseding decision (F02); ADR-0005's "one entry plus one HTTPRoute" consequence is stale (F05); the kustomize checksum duplication undermines the Renovate regex-manager story (F07).

### Security — 6
Supply chain is good where it was built for: SHA-pinned actions, checksum-verified tool installs, cosign keyless signature plus provenance attestation, digest-pinned deployment, gitleaks over full history with value-only allowlisting, CORS correctly denies a foreign origin. The dimension is pulled down by the trust anchor: a public, unprotected, unsigned `main` that CI writes to and a cluster-admin Argo CD auto-applies (F02); one broad personal token shared across Terraform, CI and the cluster, with the canonical doc still prescribing exactly that (F03); a validation bypass on the one commit per release that edits manifests (F08).

### Operability — 7
The runbook additions in `bedbc29` are exactly what a 3 a.m. stranger needs: the duplicate-operator release-name trap with its symptom, the two Cilium identity gotchas with Hubble output, the SSA-default hunt via `managed-resources`, the DNS-01 token constraint, and a concrete verify list including the preflight and round-trip. `web-deploy-failure.txt` and the BACKLOG make the deploy blocker legible. Deductions: four documents give four different token scope lists and the canonical one is wrong (F03); the CNP invariant lives in a comment and a runbook sentence rather than a check (F05); the branch-protection reminder was dropped from the BACKLOG (F02); evidence files are UTF-16 (F06).

## What was done well
- Root-causing the Gateway 403 and the CNPG API-server denials with Hubble verdicts rather than guesswork, and fixing them at the identity layer (`fromEntities: [ingress]`, `toEntities: [kube-apiserver]`) with the symptom, the tool, and the reason recorded in the manifests and the runbook — the next operator will not rediscover cilium/cilium#47617.
- Spelling out webhook/API-server defaults (`plugins[].enabled`, `parentRefs[].group/kind`, `backendRefs[].group/kind/weight`, catch-all `matches`) instead of reaching for `ignoreDifferences`: Git stays the complete truth and Argo CD's SSA diff is now meaningful; the runbook documents how to find the next one via `managed-resources`.
- Replacing the gitleaks action with the checksum-verified pinned CLI over full history, and allow-listing by exact value never by path, so a real credential in the same file still fails.
- The bump step extracts kustomize to `mktemp -d`, aborts when the overlay is already at the SHA, and rebases-and-retries the push — the earlier stray-file and race failures cannot recur.
- Production integrity is provable without trust: the running image digest equals the committed overlay digest, and every `_astro/*.js` content hash served by production equals a local build of HEAD.
- Moving www→apex to a zone Single Redirect and having `check-dist.mjs` reject absolute URLs in `_redirects` (Workers error 100324) turns a deploy-time failure into a build-time one.
